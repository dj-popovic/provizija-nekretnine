# API Contract — Real Estate Website Backend (MVP)

## Document purpose

This document defines the public MVP API contract for the real-estate website backend. It is written as a human-readable contract in Markdown and serves two purposes:

1. a clear implementation guide for the backend
2. a practical integration contract between frontend and backend

This is not a full OpenAPI specification. The goal of this document is clarity, consistency, and easy implementation in Claude Code.

---

## API scope

### Included in MVP

The MVP contract includes these public endpoints:

- `GET /api/home`
- `GET /api/properties`
- `GET /api/properties/:slug-id`
- `GET /api/filter-options`
- `GET /api/agents`
- `GET /api/agents/:slug`
- `GET /api/health`
- `GET /api/status`
- `POST /api/contact`
- `POST /api/inquiries/property`
- `POST /api/inquiries/agent`
- `POST /api/advertise-property`

### Explicitly out of MVP

The MVP does not include:

- authentication endpoints
- admin endpoints
- protected/internal management endpoints
- CMS-like content management endpoints
- dynamic FAQ / CTA / buying-process content endpoints
- generic filter facets on the listing response (the one exception is `GET /api/filter-options`: locations and present property types, approved for #15 on 2026-10-20)

---

## Response conventions

### Payload format

All request and response payloads use JSON, except standard HTTP path params and query params.

### Success response wrappers

Single-resource responses use:

```json
{
  "data": {}
}
```

Collection/list responses use:

```json
{
  "items": [],
  "pagination": {}
}
```

### Error response shape

All endpoints should use the same MVP error shape:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request body is invalid.",
    "details": [
      {
        "field": "email",
        "message": "Email is required."
      }
    ]
  }
}
```

#### Error fields

- `code` — stable programmatic error identifier
- `message` — short human-readable message
- `details` — optional field-level validation details

### Standard HTTP status codes for MVP

The API should document and use these standard status codes where applicable:

- `200 OK`
- `201 Created`
- `400 Bad Request`
- `404 Not Found`
- `413 Payload Too Large` — request body over the size limit (`PAYLOAD_TOO_LARGE`)
- `415 Unsupported Media Type` — POST body is not JSON (`UNSUPPORTED_MEDIA_TYPE`). The API accepts `application/json` only; `text/plain`, urlencoded and multipart bodies (the ones another website can send cross-site without a CORS preflight) are refused before any handler runs.
- `429 Too Many Requests`
- `500 Internal Server Error` — only for unexpected server failures, never for client mistakes

## 2. GET /api/properties

### Purpose

Returns the public property listing with filtering, sorting, and pagination.

This is the single listing endpoint for all property browsing modes, including purchase/sale and rent flows.

### Used by page(s)

- Properties listing page
- Home page search redirect target
- Any filtered search results page

### Query/path params

Supported MVP query params:

| Param | Repeatable | Meaning |
|---|---|---|
| `transactionType` | no | `sale` or `rent` |
| `propertyType` | yes | type key(s); several = any of them. "Poslovni prostor" in the UI sends `commercial` + `office` |
| `city` | no | exact city name as listed by `GET /api/filter-options` (case-insensitive) |
| `hood` | yes | district(s) of `city`; several = any of them. **Requires `city`**: a district name is only unique within its city ("Okolina") |
| `roomsMin`, `roomsMax` | no | inclusive rooms range, positive numbers; a studio (garsonjera) is `0.5`. Listings without rooms (plots, farmland) never match |
| `priceMin`, `priceMax` | no | inclusive, €; "cena na upit" never matches a price filter |
| `areaMin`, `areaMax` | no | inclusive building area in **m²**; plots / farmland (no building area) never match |
| `landAreaMin`, `landAreaMax` | no | inclusive plot area in **ares** (the `landArea` value); apartments and listings without a plot area never match |
| `page`, `pageSize` | no | pagination (`pageSize` ≤ 100) |
| `sort` | no | see below |

"Više filtera" (#16). Every rule works on the values the site shows (spec panel, feature chips); a listing without the value never matches a set filter.

| Param | Repeatable | Meaning |
|---|---|---|
| `newBuild` | no | `true` = Novogradnja tab: listings with feature `new_build` or `under_construction` |
| `bathroomsMin` | no | at least this many bathrooms |
| `floorMin`, `floorMax` | no | inclusive floor range, **apartments only**; prizemlje = `0` |
| `notGroundFloor` | no | `true` = apartments with a known floor above prizemlje |
| `notTopFloor` | no | `true` = apartments with a known floor below `totalFloors` |
| `yearMin`, `yearMax` | no | inclusive construction year range |
| `heating` | yes | **any of** the heating keys (`central`, `gas`…; unmapped XML values pass through as-is) |
| `furnished` | yes | **any of** the furnishing keys (`furnished`, `semi_furnished`, `empty`) |
| `construction` | yes | **any of**: `new` (Novogradnja), `under_construction` (U izgradnji), `old` (Stara gradnja) |
| `condition` | yes | **any of**: `original` (Izvorno stanje), `renovated` (Renoviran), `needs_renovation` (Za adaptaciju) |
| `registered` | no | `true` = only `registration: "registered"` (Uknjižen) |
| `feature` | yes | **all of** the feature-chip keys (see the Features table); only features the site shows for that type count (no `elevator` for houses) |
| `equipment` | yes | **all of**: `air_conditioning` (Klima), `internet`, `cable_tv` (Kablovska), `intercom` (Interfon), `video_intercom` (Video interfon), `video_surveillance` (Video nadzor) |

Switches (`newBuild`, `notGroundFloor`, `notTopFloor`, `registered`) accept `true` / `1` / `false` / `0`; anything else → `400`. Unknown `feature`, `equipment`, `construction`, `condition` keys → `400`.

Example: `/api/properties?transactionType=sale&city=Novi%20Sad&hood=Telep&hood=Grbavica&roomsMin=2&roomsMax=3`

#### Query param notes

- `transactionType` is a main filter and should be supported.
- Do not create separate endpoints for sale/rent tabs. Those are variants of this same route.
- The endpoint does not return filter metadata/facets. Filter choices come from `GET /api/filter-options`.
- Repeat a param to give several values (`hood=a&hood=b`); commas are not separators.
- Validation → `400 VALIDATION_ERROR` with `details`: `hood` without `city`; a non-repeatable param given twice; a non-numeric or negative number (`roomsMin` / `roomsMax` must be > 0); any `…Min` greater than its `…Max`; more than 50 values of one param.
- The old `location` and `rooms` params were removed in #15 (2026-10-20) and are ignored like any unknown param.

#### Suggested sort values

- `newest`
- `priceAsc`
- `priceDesc`

### Request body

None.

### Success response

```json
{
  "items": [
    {
      "id": "123",
      "slug": "moderan-dvosoban-stan-liman-2",
      "url": "/nekretnine/moderan-dvosoban-stan-liman-2-123",
      "title": "Moderan dvosoban stan",
      "transactionType": "sale",
      "propertyType": "apartment",
      "location": "Novi Sad, Liman 2",
      "price": 154500,
      "images": [
        {
          "url": "https://example.com/image-1.jpg",
          "alt": "Moderan dvosoban stan"
        },
        {
          "url": "https://example.com/image-2.jpg",
          "alt": "Dnevna soba"
        }
      ],
      "area": 52,
      "landArea": null,
      "rooms": 2,
      "highlights": ["Terasa", "Lift", "Parking"]
    }
  ],
  "pagination": {
    "page": 1,
    "pageSize": 12,
    "total": 245,
    "totalPages": 21
  }
}
```

### PropertyListItem fields

`PropertyListItem` should include these core MVP fields:

- `id`
- `slug`
- `url`
- `title`
- `transactionType`
- `propertyType`
- `location`
- `price`
- `images`
- `area` — building area in m²; `null` for plots / farmland
- `landArea` — plot area in **ares**; `null` for apartments or when not provided
- `rooms`

Optional / when available:

- `highlights`

Note: `propertyType` in list items is currently the Serbian label (e.g. `"Stan"`), not the key shown in the examples. It switches to the stable key during the i18n migration.

Area rule: `area` (m²) and `landArea` (ares) are never mixed. A plot shows only `landArea`. A house can have both.

### Image shape

The listing response should not use only `primaryImage` as a single string field.

Instead, it should use:

- `images` as an array of simple image objects

This supports slider cards on the frontend. The frontend can treat the first image as the default primary image.

Suggested simple image shape:

- `url`
- `alt`

### Response notes

The listing response should not include:

- `agentSummary`
- filter metadata / facets / available filter values (those come from `GET /api/filter-options`)

### Error responses

- `400` for invalid query params
- `500` for unexpected backend errors

### Notes

- `page` and `pageSize` should be parsed and validated on the backend.
- If `sort` is omitted, backend should apply a stable default sort, preferably `newest`.
- Image `alt` text is derived from the property title.
- `url` is a canonical relative frontend path generated by the backend using pattern `/nekretnine/:slug-:id`.
- `highlights` are derived from `<other>` XML elements (curated subset, TBD during implementation).

### Specs object (specification panel)

`specs` holds everything the specification panel needs. Enumerable values are **stable English keys** that the frontend translates (sr / en / ru). Unknown XML values that have no key yet are passed through unchanged (Serbian text).

| Field | Type | Notes |
|---|---|---|
| `propertyType` | string | key: `apartment`, `house`, `plot`, `land`, `commercial`, `office`, `garage`, `other` |
| `area` | number \| null | m². `null` for plots / farmland |
| `landArea` | number \| null | **ares**. Always `null` for apartments |
| `location` | string | `"City, Hood"`; never a street or number |
| `rooms` | number \| null | may be fractional (`2.5`) |
| `bathrooms` | number \| null | |
| `floor` | string \| null | `"ground"` (prizemlje) or a floor number as string. Apartments only |
| `totalFloors` | number \| null | Apartments only |
| `furnished` | string \| null | key: `furnished`, `semi_furnished`, `empty` |
| `heating` | string[] | keys: `central`, `gas`, `underfloor`, `solid_fuel`, `norwegian_radiators`, `storage_heater` |
| `registration` | string | `registered`, `in_progress`, `unregisterable`, `not_registered`. **Never null:** a missing value means `not_registered` |
| `constructionYear` | number \| null | |

Type rules applied by the backend: `floor` / `totalFloors` only for apartments. Plots and farmland (`plot`, `land`) have only `propertyType`, `landArea`, `location` and `registration`; the other fields are `null` or `[]`. A `null` / empty field means the frontend skips that row.

The flat fields `area`, `rooms`, `bathrooms`, `floor`, `heating`, `furnished`, `elevator`, `registrationStatus` are kept for backward compatibility during the i18n migration and will be removed once the frontend reads only `specs`.

### Features (feature chips / "kvadratići")

`features` is an array of stable keys, **already ordered by display priority** (most interesting first), at most 12. It never repeats spec-panel data (area, rooms, bathrooms, floor, registration). An empty array means no chips.

Priority order and keys:

| Group | Keys (XML `<other>` value) |
|---|---|
| Standout | `penthouse` (Penthouse), `villa` (Vila), `duplex` (Duplex), `luxury` (Lux), `pool` (Bazen) |
| Notable | `pet_friendly` (Pet friendly), `new_build` (Novogradnja), `under_construction` (U izgradnji), `salon` (Salonski) |
| Amenities | `elevator` (Lift), `terrace` (Terasa), `garage_space` (Garažno mesto), `parking` (Parking), `basement` (Podrum), `storage` (Ostava) |
| Infrastructure | `paved_road` (Asfaltni put), `city_water` (Gradska), `city_sewage` (Gradska kanalizacija) |
| Permits | `building_permit` (Građevinska), `location_permit` (Lokacijska), `occupancy_permit` (Upotrebna) |
| Condition / buying | `renovated` (Renoviran), `move_in_ready` (Odmah useljiv), `mortgage_eligible` (Može na kredit) |

Type rules applied by the backend:
- infrastructure keys only for `house`, `plot`, `land` (apartments always have them, so they're noise there)
- permit keys only for `plot`, `land`
- `elevator` never for `house`, `plot`, `land`

The legacy `highlights` field (Serbian labels) is kept for backward compatibility and will be removed during the i18n migration.

### Property code ("šifra")

`code` is the agency property code, parsed from the `ŠIFRA NEKRETNINE: <code>` / `ŠIFRA OGLASA: <code>` prefix of the XML `property_name`. The prefix is removed from `title`. `code` is `null` when the XML title has no code. `code` is a display value only; `id` stays the identity.

### Address rule

The public API does **not** expose the street, street number or flat number. The only public location is `location` (`"City, Hood"`).

The backend keeps the street fields internally, but no public response includes them.

### Missing-data behavior

For some fields, such as `furnished`, the XML may not always provide data.

In those cases:

- backend may return `null` or omit the field
- frontend may render a fallback label such as “Nema podatak”

### Related properties rule

`relatedProperties` should be embedded in the same property detail response, not exposed as a separate MVP endpoint.

Selection ("Slične nekretnine", agreed with the client):
- up to **6** properties, never the property itself
- same `transactionType` only (sale with sale, rent with rent); **not** restricted by city
- same property type first, ranked by **relative price distance** (`|Δprice| / price`); if fewer than 6 of the same type exist, the remaining slots are filled with other types, also by price distance
- "cena na upit" properties (`price: null`) are never suggested; for a "cena na upit" property, only same-type properties are suggested (newest first), since there's no price to compare
- the selected properties are returned **most similar first** (same type first, then the closest price first); ties go to the newer listing

### Price on request ("cena na upit")

RELPER requires a price, so agents enter a symbolic **1 €** for "cena na upit". For such properties the API returns `price: null` (in `PropertyListItem`, `PropertyDetail` and related items), and the frontend shows "Cena na upit". They are excluded by any `priceMin` / `priceMax` filter and are sorted last for both `priceAsc` and `priceDesc`.

### Error responses

- `404` if property with given ID cannot be resolved
- `500` for unexpected backend errors

### Notes

- `relatedProperties` should use list-item-like summary objects, not full detail objects.
- Image `alt` text is derived from the property title.
- `url` is a canonical relative frontend path generated by the backend using pattern `/nekretnine/:slug-:id`.
- `highlights` are derived from `<other>` XML elements (curated subset, TBD during implementation).
- `registrationStatus` (legacy flat field) is a three-state string derived from `<other>` XML values: `"registered"`, `"unregisterable"`, `"in_progress"`, or `null`. `specs.registration` maps `null` to `"not_registered"`.
- `propertyType` (flat field) is the Serbian label (legacy). `specs.propertyType` is the stable key.

## 3a. GET /api/filter-options

### Purpose

Returns the choices the listing filters offer, built from the runtime dataset: every city with its districts (`property_hood`, exactly as RELPER sends them; `hood_part` is not used), with counts, and the property types present.

### Used by page(s)

- Properties listing page (Grad / Deo grada dropdowns, the extra type chips)
- Home page hero (Lokacija picker)

### Query params

**The same filters as `GET /api/properties`** (same names, same validation, same `400`): the frontend sends the filter panel as it is on screen, so the counts follow the whole combination (e.g. Stan + Novi Sad + Telep). `page`, `pageSize` and `sort` are accepted and ignored.

What is **listed** depends only on the tab: `transactionType` (`sale` / `rent`) and `newBuild` (Novogradnja). The other filters only change the **counts**, so the lists don't jump while the user clicks.

### Success response

```json
{
  "data": {
    "propertyTypes": [
      { "key": "apartment", "count": 17 },
      { "key": "house", "count": 7 },
      { "key": "plot", "count": 1 }
    ],
    "cities": [
      {
        "name": "Novi Sad",
        "count": 21,
        "hoods": [
          { "name": "Adamovićevo Naselje", "count": 2 },
          { "name": "Telep", "count": 6 }
        ]
      },
      { "name": "Bač", "count": 1, "hoods": [] }
    ],
    "counts": {
      "feature": { "terrace": 19, "elevator": 12, "parking": 8 },
      "equipment": { "air_conditioning": 16, "intercom": 12 },
      "heating": { "central": 12, "gas": 8 },
      "furnished": { "empty": 9, "furnished": 9 },
      "construction": { "new": 9, "old": 10 },
      "condition": { "original": 3, "renovated": 4 },
      "registration": { "registered": 11, "in_progress": 1 }
    }
  }
}
```

### Response notes

- `propertyTypes`: every type key with at least one listing in the tab (the most common first). The frontend shows an extra type chip (e.g. `garage`) only when its key is here. `count`: listings of that type matching only the panel's **location and price** (`0` → that type chip is dimmed: e.g. no Plac in Telep). The other filters are left out on purpose: switching the type clears the ones that don't fit the new type (rooms for a plot, Terasa, m² ↔ ares), so they must not block the switch.
- `cities`: every city with at least one listing in the tab, the biggest first (by all its listings in the tab, so the order never jumps); ties A–Ž.
- `hoods`: the city's districts in Serbian alphabetical order. `[]` when no listing of that city has a district (e.g. Bač).
- City / district `count`: listings matching the panel **without its location choice**, so every other city and district stays pickable. It can be `0` (dimmed in the dropdown).
- Names are grouped case-insensitively; the first spelling seen is returned. A listing without a district counts toward its city only.
- Use `name` values as-is for `city` / `hood` in `GET /api/properties`.
- `counts`: for each "Više filtera" group, how many listings have each value together with the rest of the panel. Only values with at least one listing appear; a missing key means 0 (the frontend dims and disables that chip).
  - "any of" groups (`heating`, `furnished`, `construction`, `condition`, `registration`) are counted **without their own choice**: choosing Centralno doesn't dim Gas.
  - "all of" groups (`feature`, `equipment`) are counted **with every choice**: after Lift, a feature no listing with a lift has is 0.
  - `feature` counts only features the site shows for the listing's type.

### Error responses

- `400` for invalid query params (the same rules as `GET /api/properties`)
- `500` for unexpected backend errors

## 4. GET /api/agents

### Purpose

Returns the list of public agents.

# Shared conventions / common notes / naming rules

## 1. Base path

All public MVP endpoints use:

- `/api`

## 2. Resource wrappers

Use:

- `{ "data": ... }` for single-resource responses
- `{ "items": [...], "pagination": ... }` for collection responses

## 3. Pagination metadata

Collection endpoints that paginate should use:

- `page`
- `pageSize`
- `total`
- `totalPages`

## 4. Optional/null behavior

Because property data comes from an external XML source of truth, not all fields are guaranteed to exist for every record.

The contract should therefore allow some fields to be:

- `null`
- omitted

This is especially relevant for:

- optional property detail fields
- optional agent enrichment fields
- optional listing highlights
- optional media or descriptive fields

Frontend should handle missing data gracefully.

## 5. Validation documentation rule

For MVP, validation rules should be documented at the level of:

- required vs optional
- basic type expectations
- basic format expectations
- enum-like allowed values where needed

Do not over-document low-level validation constraints unless they are especially important.

## 6. Naming rules

Use normalized English field names in public API payloads where practical.

Examples:

- `transactionType`
- `propertyType`
- `priceMin`
- `priceMax`
- `areaMin`
- `areaMax`
- `fullName`

## 7. Property identity rule

The authoritative property identity is the XML `property_id`.

Public property detail route uses:

- `:slug-id`

But lookup is ID-driven, not slug-driven.

## 8. Agent identity rule

Internal XML-driven agent identity is `id_agent` (integer). In the public API, this is exposed as `agentId` (camelCase).

Public agent page route uses:

- `:slug`

For inquiry submission, the request should use:

- `agentId`

## 9. Home endpoint rule

`GET /api/home` should remain small and only include truly dynamic home-page sections in MVP.

Do not mix in static page content unless it becomes intentionally backend-driven later.

## 10. Listing endpoint rule

`GET /api/properties` is the single listing endpoint.

Do not split sale/rent/filter variants into separate routes.

Use query parameters instead.

## 11. Image rule

Where multiple property images are needed, use:

- `images` as an array of simple image objects

Do not rely only on a single `primaryImage` string if the UI expects a slider/gallery.

The internal image model uses `{ url, order }`. The API layer uses `{ url, alt }` where `alt` is derived from the property title.

## 12. Operational endpoints rule

`GET /api/health` and `GET /api/status` should remain shorter and simpler than main business endpoints, but still be documented in the same file.

## 13. Static frontend content rule

FAQ, buying-process, counters, CTA blocks, and similar static sections remain outside backend contract in MVP unless they later become dynamic.
